# ADR 009: リスクベース運用設計（Phase 0）の導入

## 1. 背景と課題
従来の「11の手順」の一律適用は、軽微なバグ修正（タイポや文言変更など）に対しても過剰な検証コスト（再現環境の固定や独立検証基準の策定）を強制し、AIによる開発のROIを著しく低下させていた。また、「自動テストが書けないバグ」に対して偽の証拠を量産する「進捗宗教」に陥るリスクがあった。

## 2. 決定事項
不具合の重大度と検証可能性に基づく「3段階のルート（Light/Standard/Strict）」を正式なガバナンスとして導入し、Phase 0として以下の物理的制約を実装した。
- **自動一次判定 (Triage)**: `core_config.json` に `T3_force_paths` を定義し、セキュリティや統治に関わるパスへの変更は自動的に T3（厳格）として処理し、AIの自己申告によるルート誤分類を防ぐ。
- **Standardルートの回帰テスト必須化**: T2ルートでは、既存CIの通過に加え、「バグを再現する新規回帰テストの追加」を必須条件とした。
- **フックスクリプトの拡張**: `.agents/scripts/write-safety-check.js` および `done.js` を拡張し、パスベースの制約違反や、回帰テスト・最小トレース（1行ログ）の欠如を警告・ブロックするロジックを組み込んだ。

## 3. 今後の展望 (Phase 1〜3)
- 過去のバグを用いたシミュレーション（Phase 1）を実施し、Human-to-AI Cost Ratio や誤分類率（テールリスク）を測定する。
- 軽微ルートのサンプリング監査や、CI/CDパイプライン上でのAIメタエージェントによる完全自動トリアージを段階的に導入する。
